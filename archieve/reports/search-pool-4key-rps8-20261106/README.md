# 四个真实 key 的单 key 8 RPS 验证

本轮分别观察四个 key，使用正式 search_pool.py / serper_proxy.py 实现，测试不改正式配置。测试 key 在生产 Redis 中临时隔离，其余 key 继续可用；结束后合并用量并恢复 key，保留真实限流状态。所有临时隔离已清除，正式 health/check 正常。

## 实测

每阶段提供 20 秒固定速率流量，随后等待已发送请求结束。先测每 key 8 RPS、并发槽位 32（排除原 2 并发瓶颈）；冷却结束后，同样四个 key 测 2 RPS/32 并发，再测具体候选配置 2 RPS/6 并发。

| key 指纹（非密钥） | 8 RPS 上游尝试 | 8 RPS 成功 | 8 RPS 上游 429 | 2 RPS/6 并发成功 | 2 RPS/6 并发全程成功 RPS | 端到端 P95 秒 |
|---|---:|---:|---:|---:|---:|---:|
| K1（bd63167b307f） | 30 | 25 | 5 | 40/40 | 1.784 | 4.022 |
| K2（e99aa2751085） | 31 | 27 | 4 | 40/40 | 1.714 | 4.126 |
| K3（61cedba8e78a） | 33 | 26 | 7 | 40/40 | 1.751 | 4.724 |
| K4（0807b7b8bc1a） | 30 | 25 | 5 | 40/40 | 1.816 | 3.621 |

8 RPS 阶段每 key 共提交 160 次 API 请求；四个 key 均在约 4.1–4.5 秒收到首次上游 429，后续本地请求因为冷却而被拒绝。实际只发出 124 次上游尝试，其中 103 次成功、21 次 429。**冷却后的平均成功 RPS 不能用作 key 的稳定容量。** 同时测四个 key，总目标为 32 RPS；现有证据不能进一步区分供应商按 key、共享账号、出口 IP 或并发数限流，因此不能声称单 key 的固有上限必然小于 8。

2 RPS/32 并发阶段 160/160 成功、零 429；全程单 key 成功 RPS 为 1.749–1.823。候选 **2 RPS + 每 key 6 并发** 同样 160/160 成功、零 429，全程最差单 key 为 **1.714 RPS**。全程分母包括冷启动和尾部收尾；从第 5 秒起的完整 5 秒窗口中，候选配置最小完成率为 1.8 RPS。

建议：单 key 发起速率先保持 2 RPS；若需要尽量达到这个速率，可采用本次测试通过的 6 并发候选值。容量规划暂按 **1.5 成功 QPS/key** 留余量，这是基于短测的保守规划值，不是统计置信下界或长期承诺。本次没有探测 3–7 RPS，也没有证明 2 RPS 是最大稳定速率。

正式配置仍为 **2 RPS/key + 2 并发/key**，未自动应用候选 6 并发。2 RPS 的实测上游平均耗时约 1.8 秒，原 2 并发可能先于 RPS 限制成为瓶颈；不能直接把候选测试吞吐当成现有正式配置的吞吐。
